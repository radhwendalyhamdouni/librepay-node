# Security

## Threat model

LibrePay Node defends one asset: **the operator's money**. The design goal is
that even a *full compromise of the node process* must not let an attacker
steal funds — only deny service.

## Key custody boundaries

| Secret | Lives where | What a thief gets |
|---|---|---|
| `LP_ZPUB` / `LP_PAYMENT_CODE` | `.env` | Nothing spendable — public keys only. Worst case: they can derive (already public on checkout) future addresses. |
| phoenixd 24-word seed | phoenixd's data dir, printed once at first run | **Lightning balance** — this is why Lightning funds stay small. |
| On-chain private keys | YOUR wallet, offline by definition | Never on this machine. |
| `LP_API_KEY`, `LP_WEBHOOK_SECRETS`, `LP_APP_SECRET` | `.env` | Ability to create invoices / forge webhook calls to your endpoints. Revoke by regenerating. |

**The node never holds an on-chain spending key. There is nothing to drain
on-chain.**

## Controls in depth

- **API auth** — `lp_live_<48hex>` keys, timing-safe sha256 comparison,
  IP-rate-limited key lookups (60/min), creation rate limits (120/min).
- **Webhooks out** — HMAC-SHA256 over the RAW body, `sha256=` prefixed,
  delivered with `redirect: "manual"` and re-validated through an
  SSRF guard **at delivery time** (DNS rebinding / private-address escapes
  are rejected, and a 30x cannot bounce a signed payload internally).
- **Webhooks in** (phoenixd → node) — bound to the internal network only in
  the compose setup; no published ports.
- **Input validation** — every mutating endpoint parses through Zod schemas
  with explicit caps (metadata ≤32 keys / ≤256-char values, description ≤140…).
- **State machine integrity** — status transitions are atomic
  compare-and-set, never move backwards, and settlement events fire exactly
  once (notified flags) — safe under concurrent cron ticks and webhook storms.
- **No unsafe redirects** — `checkoutUrl` is built from `LP_BASE_URL` or the
  request host only; no user-controlled redirect surface.
- **Headers** — CSP without `unsafe-eval`, `X-Frame-Options: DENY`,
  `frame-ancestors 'none'`, nosniff, strict referrer policy.

## Reporting a vulnerability

Email the operator contact published in the repository README (or open a
GitHub security advisory). Please do not open public issues for
exploitable findings. We commit to acknowledging within 72h.

## Before exposing to the internet

- [ ] `LP_APP_SECRET` and `LP_API_KEY` generated by `bun run setup` (not hand-typed)
- [ ] phoenixd seed backed up **offline**, data dir not world-readable
- [ ] `.env` permissions `600`, owned by the service user
- [ ] TLS via Caddy/nginx **or** Tor-only operation
- [ ] `LP_SIMULATE` unset/false — simulate mode can settle invoices for free
- [ ] firewall: only 80/443 (or nothing but onion) reachable; phoenixd port never exposed
